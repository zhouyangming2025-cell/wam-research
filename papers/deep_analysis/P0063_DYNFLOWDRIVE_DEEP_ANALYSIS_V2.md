# 1. Executive verdict

DynFlowDrive combines three mechanisms that must be separated:

```text
A. a standard multimodal trajectory planner
B. a training-only trajectory-conditioned latent flow model
C. a training-only world-dynamics-aware mode-selection teacher
```

The clean training graph is:

```text
current observation
→ scene queries / planner representation
→ N candidate trajectories + N learned mode scores

current/future observations
→ pretrained VAE-derived world latents z_t , z_{t+1}

for candidate n:
(z_t + trajectory T_n)
→ rectified-flow velocity field over s∈[0,1]
→ predicted endpoint / reconstruction discrepancy
→ transport-path direction consistency S_theta^n

GT trajectory error L_traj^n
+ future-latent reconstruction L_rec^n
+ flow-path stability S_theta^n
→ criterion C_n
→ n* = argmin_n C_n
→ n* supervises the planner's score head

plus:
trajectory loss + score loss + reconstruction loss + flow loss
→ joint training gradients
```

The deployed graph is much simpler:

```text
current observation
→ planner
→ candidate trajectories + learned scores
→ argmax learned score
→ final trajectory

FLOW WORLD MODEL = ABSENT
FUTURE LATENT = ABSENT
FLOW STABILITY COMPUTATION = ABSENT
```

Thus its core lifecycle is closer to:

> **world-dynamics-derived supervision distilled into a model-free deployed scorer**

than to WoTE / World4Drive-style online consequence evaluation.

# 2. Host planner first: the candidates exist before the world model

DynFlowDrive begins from a conventional multimodal planner:

```text
multi-view sensor observation
→ scene encoder / scene queries Q_scene
→ trajectory queries Q_traj
→ cross-attention to scene
→ residual trajectory head
→ candidate trajectories T_hat^1...T_hat^N

same trajectory-query features
→ score head
→ c^1...c^N
```

The world model does **not** create the action space. It receives candidates generated by the planner.

This ordering matters:

```text
candidate support / proposal quality
→ already fixed before world reasoning

world model
→ changes candidate supervision / ranking target
```

Horizontal comparison:

```text
WoTE
256 anchors → scene refinement → online recurrent BEV futures → utility → argmax

WorldDrive
256 anchors → coarse planner → top-K → distilled future-aware ranking online

World4Drive
6 intention-conditioned trajectories → 6 endpoint futures → ScoreNet online

DynFlowDrive
candidate trajectories → TRAINING-ONLY flow dynamics → n* label
→ deployed score head selects without future modeling
```

Therefore DynFlowDrive is not simply another `candidate → predicted future → score at test time` method.

# 3. Current and future world representation

## 3.1 Planner state and world-model state are related but not identical

The planner first forms ordinary scene queries from visual features.

The world model introduces a separate representation path:

```text
view image I_t^i
→ pretrained VAE encoder E_vae
→ lightweight MLP
→ per-view latent z_t^i

{z_t^i} + planner scene queries Q_scene
→ cross-attention
→ world latent z_t^w
```

The same procedure on the **actually observed next frame** produces:

```text
z_{t+1}^w
```

which is the factual future target.

The paper figure marks world encoders with snowflake icons, suggesting a frozen foundation encoder, but the text does not explicitly state the exact freeze policy and code is unavailable. Record this as:

```text
pretrained VAE foundation representation = PAPER-VERIFIED
exact trainability/freeze semantics        = SOURCE-UNVERIFIED
```

## 3.2 Imported-prior attribution is nontrivial

Table 4 reports:

```text
Static WM                    0.61 L2 / 0.30 CR
Flow WM                      0.59    / 0.26
Flow WM + World Feat Design  0.57    / 0.22
```

So the final improvement is not a pure `rectified flow` effect.

A substantial part comes from changing the representation source to the pretrained world-feature design.

Binding interpretation:

```text
flow dynamics gain
!=
foundation world-feature gain
```

This is the same attribution discipline already required by WorldDrive and World4Drive.

# 4. Exact action → world condition

For candidate `n`, DynFlowDrive embeds the whole predicted ego trajectory:

```text
TrajEmb(T_hat_n)
```

and concatenates it with the current world latent:

```text
h_t^n = Concat[
    lambda_z * z_t^w,
    lambda_T * TrajEmb(T_hat_n)
]
```

The flow Transformer receives:

```text
x_s
+ flow coordinate s
+ condition h_t^n
```

and predicts a velocity field:

```text
v_theta = F_theta(x_s, s, h_t^n)
```

Thus:

```text
candidate-specific output branching = YES
trajectory-conditioned flow field    = YES
shared flow model across candidates  = YES
```

But this does **not** establish candidate-specific counterfactual truth, because all candidate branches are still anchored to one factual future target from the log.

# 5. What does the flow model actually learn?

## 5.1 The factual endpoint

The only observed world future is:

```text
z_{t+1}^w
```

extracted from the one actually recorded next observation.

For training, DynFlowDrive perturbs the current latent:

```text
a = (1-alpha) z_t^w + alpha epsilon
```

and defines an interpolation:

```text
x_s = (1-s)a + s z_{t+1}^w
s ~ Uniform(0,1)
```

The flow network is conditioned by candidate trajectory `T_n`.

## 5.2 One factual endpoint for many candidate actions

This is the critical supervision fact:

```text
N candidate trajectories
→ N candidate-conditioned velocity fields / predicted paths

BUT

observed future targets available from the log
= ONE factual z_{t+1}^w
```

Therefore:

```text
candidate-specific world outputs                 YES
candidate-specific observed alternative futures NO
reactive other-agent counterfactual truths       NO
```

This is structurally close to the already-audited World4Drive issue:

```text
World4Drive:
K candidate-conditioned endpoint latents
vs one factual future latent

DynFlowDrive:
N candidate-conditioned flow paths
vs one factual next-step latent
```

The extra continuous path does **not** solve the counterfactual-supervision problem.

# 6. The most important correction: three different notions of "time"

DynFlowDrive's narrative uses words such as:

```text
continuous dynamics
progressive evolution
rate of change
small portion of latent evolution
```

But three clocks must be separated.

## 6.1 Physical-world time `tau`

This is actual scene time:

```text
t → t+1
```

The paper provides observed world targets only at the discrete next timestep.

There is no supervision showing that an intermediate model state at, say, `s=0.4` corresponds to a physically observed scene at `t + 0.4 Δt`.

## 6.2 Rectified-flow coordinate `s`

```text
s ∈ [0,1]
```

is introduced by the mathematical interpolation:

```text
a → z_{t+1}^w
```

It is a **generative / optimal-transport-style solver coordinate**.

Its intermediate states are generated by the chosen interpolation and learned vector field. They are not paired with intermediate physical frames.

## 6.3 Planner refinement iteration

The host trajectory decoder may iteratively refine queries, but that is another computational process entirely.

Therefore:

```text
flow integration step
!= physical future timestep
!= planner refinement step
```

This distinction survives ontology residue testing and motivates **F08 — Internal transition-coordinate / physical-time alignment**.

# 7. Why "flow stability" is not automatically physical stability

DynFlowDrive computes a velocity sequence along the flow solver path:

```text
v_1^n, v_2^n, ..., v_K^n
```

normalizes each vector and measures average directional angular change:

```text
S_theta^n
= mean_k arccos(u_k^n · u_{k-1}^n)
```

Smaller value means the latent transport direction changes less across solver steps.

The paper interprets this as smoother / more physically consistent dynamics.

The direct mathematical evidence supports a narrower statement:

> `S_theta` measures **directional consistency of the learned latent vector field along the rectified-flow coordinate `s`**.

It does **not directly measure**:

```text
physical acceleration
jerk
time-to-collision
other-agent reaction smoothness
physical energy
real intermediate scene consistency
```

because `v_theta = dz/ds`, not a demonstrated physical derivative `dz/dtau`.

Thus the binding scientific distinction is:

```text
smooth latent transport under s
!=
validated smooth physical evolution under tau
```

The metric can still be useful as a learned regularizer / ranking feature. What is unproven is the stronger physical interpretation.

# 8. Stability-aware selection is primarily a TRAINING TEACHER

This is the most important inference-graph correction.

For each candidate mode:

```text
C_n
= lambda_rec  * L_rec^n
+ lambda_traj * L_traj^n
+ lambda_theta * S_theta^n
```

Then:

```text
n* = argmin_n C_n
```

The selected `n*` supervises the trajectory score head.

At deployment:

```text
world model is not called
C_n is not recomputed
flow path is not integrated
S_theta is not computed
```

Instead:

```text
planner score head
→ predicts which candidate should win
→ highest learned score selected
```

Therefore the world model functions as:

```text
TRAINING-TIME LABEL / RANKING TEACHER
```

not as an online evaluator.

This is an important lifecycle distinction from:

```text
WoTE       world transition + reward remain online
World4Drive future latent + ScoreNet remain online
WorldDrive distilled future surrogate remains online
DynFlowDrive world/flow teacher removed; scorer remains
```

# 9. World-loss gradients may also shape the planner — but exact detach semantics are unverified

The total objective is:

```text
L
= L_traj
+ lambda_score L_score
+ lambda_rec L_rec
+ lambda_flow L_flow
```

The world latent aggregation uses planner scene queries, and the flow condition uses predicted trajectories. The paper figure also depicts a `Grad.` path.

The paper-level graph therefore indicates that world/reconstruction/flow objectives can shape upstream planner representations and trajectory features during training.

However, without released code we cannot verify:

```text
whether candidate trajectories are detached before world conditioning
whether Q_scene is detached in world-feature aggregation
whether VAE/world encoder is frozen exactly as suggested by the figure
which losses reach which planner layers
```

Thus canonical gradient claim:

```text
joint objective / paper graph suggests planner←world-loss coupling
exact tensor detach boundaries = SOURCE-UNVERIFIED
```

# 15. NAVSIM result: useful planner evidence, but NOT reactive closed-loop evidence

The paper repeatedly calls NAVSIM a `closed-loop` benchmark.

Under this repository's evaluation taxonomy, that wording is rejected.

NAVSIM v1 is a:

```text
NON-REACTIVE DATA-DRIVEN / PSEUDO-SIMULATION PLANNING BENCHMARK
```

It evaluates ego trajectories against logged / pseudo-simulated scene information; surrounding actors do not form a fully reactive closed-loop environment responding behaviorally to each ego intervention.

Therefore:

```text
DynFlowDrive 88.7 PDMS on NAVSIM
= strong non-reactive planning evidence

NOT
= proof of reactive interactive world dynamics
NOT
= proof of counterfactual other-agent response accuracy
```

This is particularly important because the paper motivates the method using how "the environment responds after ego action is executed."

The reported benchmark does not directly validate that strongest causal claim.

# 17. Counterfactuality audit

DynFlowDrive is a particularly clean example of why action conditioning and counterfactual truth must remain separate.

```text
I01 candidate-specific world output branching
= YES

I02 candidate-specific consequence supervision
= NO observed per-candidate alternative futures

I03 observed/simulated alternative-action ground truth
= NO; one factual logged next world state

I04 reactive other-agent response truth
= NO / NOT ESTABLISHED

I05 intervention-validity evidence
= ABSENT
```

The model can produce distinct latent flow paths under different candidate trajectories, but training does not observe what the real surrounding world would have done under every unexecuted candidate.

# 20. Strongest evidence / evidence boundary

## DIRECT PAPER EVIDENCE

```text
Static WM → Flow WM:
0.61/0.30 → 0.59/0.26  (Avg L2 / Avg CR)

Flow WM → + World Feature Design:
0.59/0.26 → 0.57/0.22

Selection:
none → L2 → +reconstruction → +flow stability
0.61/0.30 → 0.59/0.24 → 0.58/0.22 → 0.57/0.22

Flow integration steps:
1 / 3 / 5 / 10
0.60/0.28 → 0.59/0.23 → 0.57/0.22 → 0.59/0.24

Inference:
world model explicitly removed; learned score head selects candidate.
```

## WHAT THIS PROVES

The reported framework benefits from:

```text
1. replacing a static next-latent WM with a rectified-flow formulation;
2. using a pretrained/foundation world-feature representation;
3. using reconstruction / flow-derived information to improve score-head supervision;
4. keeping this world reasoning training-only to avoid deployment cost.
```

## WHAT THIS DOES NOT PROVE

It does not establish that:

```text
flow coordinate s is physical time;
intermediate flow states are real intermediate scenes;
angular vector-field consistency is calibrated physical stability;
N candidate branches have N true counterfactual future targets;
surrounding agents react correctly to alternative ego actions;
better latent flow fidelity monotonically causes better planning;
NAVSIM provides reactive closed-loop validation.
```

## STRONGEST ALTERNATIVE EXPLANATION

Planning gains may arise from the combined bundle:

```text
pretrained VAE world representation
+ additional future-state reconstruction supervision
+ multimodal candidate supervision
+ improved training-time positive-mode assignment
+ score-head distillation from a richer oracle criterion
+ generic regularization from the flow objective
```

rather than from identification of physically correct continuous world dynamics itself.
